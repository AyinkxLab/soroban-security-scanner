# SS-006 — Persistent storage write without TTL management

- **Severity:** low
- **Confidence:** low
- **Category:** storage

## Problem

A contract entry point writes to persistent storage but does not call
`extend_ttl`, `set_ttl`, or `bump` in the same function. Persistent entries have
a time-to-live; if it is not extended, stored data can expire and be lost.

## How it is detected

Reports persistent-storage mutations inside a public `#[contractimpl]` function
when that function contains no TTL-management call.

## Limitations

- TTL may be managed in a different entry point, so this is low confidence.
- Does not know the intended lifetime of the data.

## False positives

- Contracts that extend TTL centrally in a maintenance function.
- Data that is intentionally ephemeral.

## Remediation

Extend the time-to-live with
`storage().persistent().extend_ttl(...)` after writing persistent data that must
survive. Prefer a single documented TTL policy. Suppress the rule for functions
whose TTL is managed elsewhere.
