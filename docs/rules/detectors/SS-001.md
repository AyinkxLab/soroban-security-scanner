# SS-001 — State-changing entry point without caller authorization

- **Severity:** high
- **Confidence:** medium
- **Category:** authorization

## Problem

A public contract function mutates storage but never calls `require_auth` or
`require_auth_for_args`. Without an authorization check, any account can invoke
the function and change contract state, which can enable theft, privilege
escalation, or data corruption.

## How it is detected

For every public function inside a `#[contractimpl]` block, the detector collects
method calls. A storage mutation is any call named `set`, `remove`, `update`,
`extend_ttl`, `set_ttl`, or `bump` whose receiver expression mentions
`storage`. If the function contains no `require_auth` call, each storage mutation
is reported with its rendered call as evidence.

## Limitations

- Purely syntactic; no type or data-flow analysis.
- Authorization performed by a called contract or a helper function is not
  tracked across call boundaries.
- Does not distinguish storage keys or judge which operations are genuinely
  privileged.

## False positives

- Intentionally permissionless entry points (for example `deposit`).
- Functions whose authorization is delegated to a helper that itself calls
  `require_auth`.
- A caller that authorizes separately in a wrapper entry point.

## Remediation

Call `address.require_auth()` (or `require_auth_for_args`) for the account that
must approve the operation before mutating state. Prefer authorizing an argument
that binds approval to the specific operation rather than unconditionally
authorizing a stored admin address. Document and suppress the rule for
intentionally permissionless functions.
