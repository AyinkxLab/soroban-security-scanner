# SS-011 — Initialization entry point without a re-initialization guard

- **Severity:** high
- **Confidence:** low
- **Category:** access-control

## Problem

An initialization-style entry point (for example `initialize` or `init`) writes
contract storage without first checking whether the contract has already been
initialized. If the function stays callable after deployment, anyone can call it
again to overwrite configuration or take over privileged state.

## How it is detected

For every public function inside a `#[contractimpl]` block whose name contains an
initialization segment (`initialize`, `initialise`, `init`, `setup`,
`configure`), the function's facts — merged with its same-file helpers — are
inspected. The rule reports when the function writes storage and has **no**
authorization call and **no** storage existence read (`has`/`get`) that would act
as a guard.

## Limitations

- Heuristic: it infers the guard from the presence of an authorization call or a
  storage read, and cannot prove the guard is correct or reachable.
- A guard implemented in a different file or via a custom macro is not seen.
- Reported with **low confidence** for exactly these reasons.

## False positives

- Initializers whose guard is expressed in another module or helper file.
- Contracts that intentionally allow re-initialization (for example an upgrade
  path) and enforce it elsewhere.

## Remediation

Guard initialization by checking that the contract is not already initialized
before writing, for example:

```rust
if env.storage().instance().has(&KEY) {
    return Err(Error::AlreadyInitialized);
}
```

Alternatively, perform initialization in a constructor (`__constructor`) so it
runs only at deploy time.
